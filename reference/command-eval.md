# Command Eval — Technical Reference

Run any qutebrowser command from a tab's runtime directory and get structured output back (status + all messages produced during execution). Bridges the gap between fire-and-forget IPC and interactive command feedback.

## Architecture

```
command.sh  ──socat──►  IPC socket  ──►  :command-eval  ──►  CommandRunner.run()
                                                │
                                   message.global_bridge.show_message
                                                │
                                         captured messages
                                                │
                                         command-result (JSON)
    command.sh  ◄──poll──  {tab_dir}/command-result
```

The key insight: `CommandRunner.run(text, safely=True)` converts `CommandError` exceptions into `message.error()` calls. By hooking `message.global_bridge.show_message` before running the command and disconnecting after, we capture every info/warning/error message the command produces.

## `TabRuntimeManager.command_eval()`

```python
def command_eval(self, tab_id_str, command, wait_ms=0):
```

### Flow

1. Validates `tab_id_str` exists in `_tab_data` and finds the tab widget via `_find_tab()`
2. Connects `message.global_bridge.show_message` to a capture lambda that appends `{level, text}` dicts to a list
3. Creates `CommandRunner(tab.win_id)` — the win_id is needed for command dispatch context
4. Calls `runner.run(command, safely=True)`:
   - `safely=True` catches `CommandError` and routes it through `message.error()`, which the hook captures
   - Unexpected exceptions are caught by a surrounding try/except and added as error messages
5. If `wait_ms > 0`: schedules `_finish()` via `QTimer.singleShot(wait_ms, _finish)` — keeps the message hook connected during the wait to capture async messages (e.g., extension load results, delayed warnings)
6. If `wait_ms == 0`: calls `_finish()` immediately
7. `_finish()` disconnects the message hook, determines status (`error` if any captured message has level `error`), writes JSON to `{tab_dir}/command-result`

### Why the tab_id matters

The tab_id is used solely to locate the runtime directory for writing `command-result`. The command itself runs in the context of the tab's window (`CommandRunner(tab.win_id)`), which affects window-scoped commands. The command does NOT run "in" the tab — `:open` still navigates whichever tab is focused in that window.

### Message hook scope

The `message.global_bridge.show_message` signal is **global** — it fires for all messages across all windows. During the brief window between connect and disconnect, any message from any source will be captured. In practice this is fine because:
- The hook is connected for only the duration of `runner.run()` (synchronous) plus optional `wait_ms`
- Most commands produce their messages synchronously during `run()`
- The `wait_ms` window is short and explicitly opt-in

## `:command-eval` Command Registration

```python
@cmdutils.register(instance='command-dispatcher', scope='window',
                   maxsplit=2, no_cmd_split=True)
def command_eval(self, tab_id: int, wait_ms: int, command: str):
```

- `maxsplit=2`: splits the argument string into exactly 3 parts — `tab_id`, `wait_ms`, and `command` (everything remaining)
- `no_cmd_split=True`: prevents the command parser from splitting on `;;` within the command string
- Cross-window tab lookup: tries current window first, then iterates `objreg.window_registry`

## Shell Script (`command.sh`)

Generated by `_write_command_script()` with hardcoded paths (socket, result file, tab_id).

### Argument parsing

| Flag | Default | Purpose |
|------|---------|---------|
| `--timeout <seconds>` | 10 | Poll timeout for result file |
| `--wait <ms>` | 0 | Async message capture window (passed to `:command-eval`) |

All remaining arguments are joined into the command string. The `:` prefix is auto-prepended if missing.

### IPC payload

```json
{"args":[":command-eval <tab_id> <wait_ms> :<command>"], "target_arg":"tab-silent", "protocol_version":1}
```

The command string is escaped (backslashes and double quotes) before JSON embedding via `sed`.

### Output formatting

When `jq` is available, parses the JSON and prints:
```
:<command> — <status>
[<level>] <message text>
```

Exit code: 0 if status is `ok`, 1 if status is `error`.

Without `jq`, falls back to `cat` of the raw JSON file.

## JSON Result Format

Written to `{tab_dir}/command-result`:

```json
{
  "status": "ok|error",
  "command": ":<command-as-sent>",
  "messages": [
    {
      "level": "info|warning|error",
      "text": "The message text"
    }
  ]
}
```

- `status`: `"error"` if any message has level `"error"`, `"ok"` otherwise
- `command`: the command string with `:` prefix (normalized via `':' + command.lstrip(':')`)
- `messages`: array of all captured messages in order; may be empty for commands that produce no output

## Patterns Reused

| Pattern | Shared with |
|---------|-------------|
